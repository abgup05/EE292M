# The sixth referee, finding by finding (version 14.2)

The referee read version 14.2 (tag `capstone-v14.2`, commit `2b56f7a`) with read-only tools and ran nothing ([its text, unedited](reviews/referee-6-version-14.2.md)). It says so itself: every "pass" or "fail" it reports for a constructed input was traced by hand and "needs a test to confirm".

What was done with the findings is less than for the fifth referee, and this file says exactly how much. Each claim about the code was read against the code at the tag. None was confirmed by a test, and no code was changed: version 14.2 is as tagged. The four findings about documents were fixed in the documents, after the tag. The seven about behaviour are recorded here as open, each with the test that would confirm it.

**Since then (19 November 2026, branch `capstone/fixes-14-3`):** findings 1, 3, 4 and 9 were each put to a test written first, seen to fail as the referee predicted, and fixed; each row below keeps what was written when the finding was only read and adds what the test showed. Findings 2 and 10 are still open and are the owner's to decide; nothing was changed for them. Tag `capstone-v14.2` is as it was.

One thing bears on the reading. The referee's brief predates version 12 and it chose what to read. It read the quote gate, the number check, the period check, the verdict rule, the filing comparison and the evidence files, and opened none of what version 14.2 added: the analytics, the audit of the argument, the corollaries, the outside and market views, the reference pack, the page. So this is a sixth reading of the older checks at a newer tag, and the analysis itself has still not been read by a referee.

## What testing the four showed

All four predictions held: the referee traced the code correctly each time. Fixing the gate moved nothing in any recording, which says two things: the recorded quotes (a stand-in's and, in the two live samples, the API model's) do not stop beside a unit, and so nothing in the repository showed the hole either. An existing test did: it expected the cut quote to be found. The period check's stricter rule also moved no measured number, for the same reason turned round: none of the golden findings, and none of the planted errors, is a fiscal label resting on a calendar date. So for findings 1 and 3 the tests written from the referee's inputs are the only evidence that the fixed behaviour differs from the old one.

## What this reading showed

The findings that matter are 1, 2 and 3, and all three are in checks that had been read by referees before. The quote gate was the first thing this project built and the claim it carries, that a number cannot be lifted out of its context, was tested for a cut inside the digits and never for a cut beside them. The meaning check was added in version 5 and measured for how often it rejects; what a "partly" does to a verdict was never asked, because nothing printed how common "partly" is until a live run's sample was committed. And the period check's doc describes the fiscal case the code returns early from.

Version 14.2's own work was not read. The next referee needs a brief that names it.
