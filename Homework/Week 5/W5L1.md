## 2. The messaging: what the project is for, and for whom

The reviewer read only the two README openings and said back: *"For a researcher or project lead deciding whether to proceed, revise or investigate further, Evidence Desk turns a question into a decision brief whose findings each cite a server-verified exact excerpt, and marks the brief PARTIAL when evidence is thin."*

That is what I wrote, and it shows the problem. Against the sentence from Week 4B ("for [who decides], who [has this problem], [project] changes [this], and we will know because [this evidence]"):

- **Who decides** is filled, but with nobody in particular.
- **Has this problem** is only implied.
- **We will know because** is empty. The openings describe mechanisms (a substring check, a PARTIAL status), not what would show the tool works.

## 3. The organization, the patterns, and what I decided

The map I drew before the review, from the hands-on: one input goes request → plan → discover → retrieve → extract → synthesize → verify → brief, through `pipeline.execute_run` and nowhere else. That part held. The three likely changes did not each have one place to go:

| Likely change | Where it would go in `capstone-v1` | Reviewer's finding |
| --- | --- | --- |
| A new input format | `fetch.py` accepts only HTML and the pipeline calls the HTML extractor directly | F5: no single place |
| A fix to the complete/partial rule | `pipeline.py`, `synthesize.py`, the Claude prompt, `export.py` and `app.js` | F1: five places, two copies of the limits |
| A new output view | `export.py` and `app.js`, each with its own status wording | F8: no shared seam |

Patterns the reviewer found in use: a strategy (`Synthesizer`, with the extractive and the Claude engine), dependency injection (the fetcher, the searcher and the clock are passed in), a pipeline (`execute_run`), a repository (`Store`), a gate (`verify_findings`), a factory (`synthesizer_from_env`), and a fallback written inline with exception handling.

| Finding | Decision | What the next version does |
| --- | --- | --- |
| F1: status rule and limits scattered over five files | Accept | One `core/limits.py` for every number and one `core/policy.py` for the verdict rule, the status rule and their wording |
| F2: `api.py` wires concrete backends and opens the database at import | Accept | A `wiring.py` composition root; `api.py` holds routes only and is built by a factory |
| F3: record types import URL policy | Accept | `core/models.py` is pure data; URL safety is checked in the API layer |
| F4: the pipeline's retrieve step does eight jobs; fallback is hard-coded twice | Accept | Ingest becomes its own module; fallback becomes a wrapper around any engine |
| F5: no single place for a new input format | Accept in part | One adapter per source kind behind a shared `Document`; not a content-type registry (reason in `Capstone/README.md`) |
| F6: interfaces live inside `pipeline.py` and `synthesize.py`; one protocol does two jobs | Accept | `core/ports.py` holds every interface; planning, assessing and summarizing are separate protocols |
| F7: a raw `"failed"` string and no finish time on a crashed run | Accept | One public function fails a run, with the enum and the time |
| F8: status wording duplicated in the export and the page | Accept | The API serves the wording; both views read it |
| F9: the README states mechanisms, not a success measure | Accept | The README opens with the full sentence, including the evidence |
| F10: the extractive engine's stance depends on template wording | Accept by removal | The deterministic engine no longer judges a stance (reason in `Capstone/README.md`) |

## 4. One suggestion, and what I decided

The reviewer's one suggestion was a single policy module that owns the status rule, the limits and the status notes, because "the complete/partial rule is the product's central claim and is currently scattered across five files, so it can drift." I took it, and it is the first thing built in the next version.

The larger decision came from the messaging finding. I could not fill the "who decides" slot honestly for a general research tool, because I am not that user. I can fill it for equity research. The next version narrows Evidence Desk to testing the claims of an investment thesis against a company's SEC filings, which is the second idea in my original pitches joined to the part of the first version that worked. The new plan is in `Capstone/README.md` and the new prompt in `Capstone/PROMPT.md`.

What the reviewer said it could not judge from the repository: whether the demo numbers are real, whether `make verify` is green, and whether a real reader's decision is served. The first two I can show; the third needs a person, and I have not tested the tool on one.

## 6. Feedback on today

The question that did the work was the first on the review list: what the project is for, and for whom. The reviewer could not answer it for version 1, and that, more than anything about modules, is why the project became a thesis desk on SEC filings and stopped being a general research tool. "One place for every change" held up later, when several agent sessions built at once. What would have helped: one "for whom" sentence that is too vague to test beside one that is sharp enough. With that pair the gap might have been caught before a review found it.
