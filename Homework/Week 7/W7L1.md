## 2. The speed: where the time goes, and one measured change

What the reviewer was given (`docs/speed.md` at that commit): a profile of the offline example run, 0.44 s, of which parsing three filings is 66%; one change, cutting the inline-XBRL header before parsing, reported as an 8% gain with the tripwire's hash unchanged; and concurrent assessment of claims, measured with a stand-in engine.

What the reviewer found:

- **The profile is of the wrong run** (F1). The offline replay takes 0.41 s. The one live measurement is 3.2 s for three filings, and a model-backed run adds seconds per claim. The header cut saves about 19 ms, under 1% of a live run. The document ranked parsing first and never said that most of a real run is EDGAR and model latency, which were not profiled.
- **The 8% does not reconcile** (F2). Parsing fell by 18.8 ms. The whole run fell by 51 ms in the profile files, and the "Other" stage, which the change cannot touch, fell by 32 ms. The same-profile gain is 12%, the benchmark gain 7.6%, the parse-only gain 4.3%. Three numbers, not reconciled.
- **A quarter of the run is unexplained** (F3). "Other" is 24% and was never broken down. It includes 24 saves, each of which opens a connection and re-serialises the whole record.
- **"No answer changed" was shown on one company** (F4). The tripwire uses NVIDIA's filings; the other seven companies were not re-checked after the change, though `make probe` exists for that.
- **The concurrency number sits next to measured results** (F5), when it measures sleeps overlapping.

The reviewer is right on all five. The measured change was real and small, and it had been reported as if it mattered and as if it were proven everywhere.

## 3. The system: the drawing, twice corrected

**The hands-on.** A model was asked to draw the project as a system from the repository, without changing a file. Three things in its drawing were wrong:

1. **No GitHub.** The only other copy of the code was missing from a drawing of where code lives.
2. **The page's JavaScript was inside the app container.** The container serves it; it runs in the browser.
3. **Nothing said what exists only on the laptop.** The database was drawn as a host directory like any other.

Those were corrected and the drawing went into the README with a table of what cannot be rebuilt.

**The review.** The reviewer then found the corrected drawing wrong in four more ways:

- It left out two kinds of outside party: the public pages a user may add to a run, and the registries the build pulls from (PyPI, the container registries). The model's first drawing had the public pages. The correction dropped them.
- One arrow said the tool containers call the app. Only the screenshot container does. The lock container writes `uv.lock` and reaches PyPI; the syntax checker only reads.
- It omitted the one-off containers that `make run`, `make probe`, `make fixtures` and `make test` start. They bypass the served app, write the same database and reach EDGAR.
- It showed the browser calling the app but not the app serving the page.

## 4. What cannot be rebuilt

The table said filings and XBRL facts can be rebuilt because "a filing never changes". The reviewer's correction (F9): a filing does not change, but `companyfacts` is a live aggregate that restatements and new filings change, the set "latest 10-K plus later 10-Qs" moves as filings arrive, and the stored text is the output of this project's parser, which changes too. So a later run cannot reproduce an earlier run's figures or even its list of filings. A run record is unrecoverable because its inputs move, not only because a model will not repeat itself.

Two more corrections: the table omitted `results/`, which is gitignored and holds every exported brief and probe report in one copy (F8); and the fixtures are "rebuildable" only as a new baseline, since recording them again would give different facts and move the tripwire (F10).

**If the disk failed today**, in the reviewer's words: lost are every run record and its stored filing text, everything in `results/`, `.env`, and any unpushed commits; not lost, if pushed, are the code, the fixtures, the cassette, the golden records and `demo/`. No reviewer decisions exist yet, so none would be lost. That last line is the real finding: the tool has nowhere to keep the one thing a person adds to it.

## 5. One suggestion, and what I decided

**The suggestion:** split the database in two. A disposable cache of filing text, keyed by content hash and stored once per filing instead of once per run; and a record holding runs and decisions, the only file that is backed up, with a documented restore. The cost, as the reviewer put it: a schema change, a cache lookup in the ingest step, and a parser-version key so stale text is never quoted.

**Decision:** take it. It is the boundary this session is about: split where the pace and the owner differ. Filing text is EDGAR's and can be thrown away; decisions are mine and cannot.
