## 3. New in this version: the decisions a person makes

Review 3 pointed out that the tool had nowhere to keep the one thing a person adds to it. Now:

- **Accept or reject each finding.** Each claim shows two verdicts: the engine's, and the one that follows by the same rule from the findings the reader accepted.
- **Save a thesis and run it again.** "What moved" compares the two newest runs: which verdicts changed, which excerpts and which filing are new.
- **The decisions are the record.** They are what `make backup` protects.

Checked on the running app (`make live-walk`): a complete run on three filings fetched live, two decisions recorded, the reviewed brief exported, the thesis saved and run twice from the cache, and "No verdict moved and no filing is new."

## 4. The hands-on: curate, test, repeat

**Curate.** `AGENTS.md` gained a section, "what an agent could not find", drafted by the session from the corrections it actually had to make and left for me to cut down:

- *Tooling:* the Docker credential-helper path; `make verify-fresh` as the gate for a tag; only one agent may start the app container; a harness worktree branches from `main`.
- *Which data is the original:* the record cannot be rebuilt; the cache and `results/` can be deleted; a cassette is never edited by hand; an answer key is never changed to make a result pass.
- *Mistakes made more than once:* a count that survives a failure upstream; testing on one company; a measurement the numbers do not support; text that comes back from a model as the model saw it.

Nothing was cut from the course's rules in that file, and it holds no overview of the repository. One procedure moved out of a README into a skill.

**The skill.** `/blind-review`, in `.claude/skills/blind-review/`: the procedure by which each version here was reviewed, which had been run three times with ad hoc prompts. Its description says when to use it and when not (not for bugs in a diff; not for the hostile referee).

**Test** (`Capstone/evidence_desk/docs/skill-test.md`):

- *Does it fire?* Three ways of asking, each in a fresh session: three of three called the skill first. A near miss ("look over the diff I have staged and tell me if there are bugs") went to `/code-review` and left this one alone.
- *Does it help?* The same task in fresh sessions, scored on six things a good reviewer brief must contain. **With the skill, 5 of 5 good. Without it, 5 of 5. In a checkout that had neither the skill nor the review notes, 5 of 5.**

The skill did not improve the result. Reading the outputs showed why: with skills disabled, the sessions found the skill's file on disk and read it anyway, and in the bare checkout they found `docs/reviews/README.md` in the main one, which listed the same steps. What the skill changed was the looking: 6.2 turns on average with it, 8.0 without, 12.0 from the bare checkout.

**Repeat.** The lecture's rule is that what helps is what the agent could not find, and this procedure was written down twice. So it now lives in one place: the README keeps the reasons and the index and points to the skill for the steps. The skill stays because it fires without a search and carries the four checklists. I cannot claim it gives a better review; the test compared briefs, not reviews.
