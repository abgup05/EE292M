### 4. We have discussed each boundary in the system (between front end and backend, data and database, or services) and whether it is real.

Verified: yes

The boundaries, and which one is not real yet:

Backend and page. This boundary is real. The backend is the pipeline plus the API. It computes every number and code anyone reads. The API serves the tables exactly as they were written, and the page only draws them. Test T17 checks that every number on the dashboard equals the same number in that participant's package.

Pipeline and API. This one is also real. The API never calls the pipeline and computes nothing new. It only serves files the pipeline wrote, and the pipeline writes them only after a whole run succeeds. A half-finished run can't reach the dashboard.

Pipeline and the network. This is real too. The pipeline service runs with networking switched off, which protects participants' free text. The app container does have a network, so only the pipeline is truly offline.

data/raw/ is never modified, and the app only reads data/processed/. This is only a convention. Every container mounts the whole repository read-write, so only the code keeps it that way. The author's own work log (§25) corrected an earlier diagram that drew these as enforced.

The app is reachable on 127.0.0.1 only. This is set in compose.yaml, but no test checks it, so a later edit could widen it without anything failing.

One participant's package from their own rows. This is real by design. Each package is built on the backend from that participant's rows alone, so the browser never receives anyone else's data.

Data and a database. There is no database. The store is a set of versioned CSV tables with a manifest.json that describes them. That's simple and reproducible, but no service sits there to enforce access. The pipeline is the only writer because of how the code is written, not because anything stops another writer.
